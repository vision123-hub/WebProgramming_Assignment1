Week 10_1: Git and GitHub

This assignment documents practical version-control work: creating and connecting repositories, recording changes, reviewing history, collaborating with branches, and publishing a personal portfolio.

1. Create a repository and connect GitHub

A Git repository stores a project's files and the history of changes. GitHub hosts a remote copy so it can be backed up and shared. For a new local project, I can initialize Git and connect the remote repository:

cd my-project
git init -b main
git remote add origin https://github.com/USER/REPOSITORY.git
git remote -v

If a repository already exists on GitHub and has commits, cloning it is usually the safer start; cloning creates the local repository and configures origin automatically:

git clone https://github.com/USER/REPOSITORY.git
cd REPOSITORY

I should not run git init again in an existing repository or replace a project's remote without a reason. I first check the repository root, current branch, status, and remote.

2. Check the working tree with git status

git status shows the current branch and whether files are modified, staged, deleted, or untracked. Checking status before and after each Git operation helps me avoid including unrelated work.

git status
git status --short --branch

Untracked files are not included in a commit until I explicitly add them. Existing local changes should be reviewed and preserved rather than discarded.

3. Stage and commit a focused change

git add selects changes for the next commit. Staging specific paths is safer than staging every file when unrelated changes are present. A commit records the staged snapshot with a short, descriptive message.

git add index.html styles.css
git status
git commit -m "Describe the portfolio improvement"

Each commit should represent a real, reviewable improvement. I check the staged files before committing so the message accurately describes what it contains.

4. Review the commit history with git log

git log shows previous commits, their messages, authors, and dates. The compact format is useful for quickly counting and reviewing meaningful work.

git log --oneline
git log --oneline --decorate

A history is useful only when commits contain genuine changes. Empty commits or invented messages do not demonstrate completed work.

5. Create and switch branches

A branch lets me develop a change separately from the main line. git branch lists branches; git checkout -b creates a branch and switches to it. git checkout can also switch to an existing branch.

git branch
git checkout -b feature/update-readme
# make and commit a focused change
git checkout main

I can also use git switch -c feature/update-readme to create and switch to a branch. Before switching, I check the working tree and commit or safely preserve work in progress.

6. Merge completed work

After a branch is reviewed and its changes are ready, I switch to the branch that should receive them, then merge the feature branch into it.

git checkout main
git merge feature/update-readme
git status

If Git reports a conflict, I inspect the conflicted files, resolve the conflicting sections, stage the resolutions, and complete the merge commit if Git requests one. I do not overwrite work without understanding the conflict.

7. Pull from and push to GitHub

git pull retrieves remote commits and integrates them into the current branch. I pull before starting work when the shared branch may have advanced. git push sends my local commits to GitHub.

git pull origin main
git push -u origin main

The -u option sets the upstream the first time I push a branch. Later, I can use git push and git pull. If local and remote histories diverge, I read Git's message, review both histories, and resolve the situation deliberately rather than force-pushing.

8. Practical project: my personal GitHub portfolio

I developed and published my portfolio in vision123-hub/portfolio on GitHub. I used Git to track real improvements, create descriptive commits, inspect the history, and push the completed work to origin main. 9. Meaningful commit requirement and reflection

The assignment requirement was at least five meaningful Git commits. My portfolio has six commits, so it exceeds the requirement by one. Each commit corresponds to actual portfolio work rather than an empty or fabricated change.

I learned that Git status helps me understand what will be recorded, staging lets me select the exact change, and commits make a useful project history. Branches support isolated work, merging brings finished work together, and pull/push keep local and GitHub copies synchronized. Reviewing the remote and history after publishing confirms what was actually delivered.
